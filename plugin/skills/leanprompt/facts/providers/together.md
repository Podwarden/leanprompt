# Together AI

Status: documented, not measured here. Facts from Together's official docs (docs.together.ai), checked on 2026-11-27 against the raw page text (the Markdown source each docs page serves at its `.md` URL). No API request was sent.

The frontmatter `cache:` block says `min_tokens: 0` because the docs give no minimum: "The minimum cacheable prefix length and the granularity of cached tokens vary by model and can change, so don't design your prompts around a specific threshold." So 0 means "not stated". `ttl_seconds: 3600` is "typically about an hour", which is the only figure given. It is not a guarantee: "under heavy load, entries may be evicted sooner". Treat it as an upper-leaning planning figure, not a floor.

## Caching

| Fact | Value | Source |
|---|---|---|
| Mode | "Prompt caching is automatic on serverless inference and dedicated model inference." "There's no parameter, header, or account setting to turn it on." The prefix is the prompt as the chat template renders it, so tool definitions and settings such as `reasoning`, `reasoning_effort` and `chat_template_kwargs` are part of it. Entries only serve requests to the same model | https://docs.together.ai/docs/inference/chat/prompt-caching.md |
| Models | The caching page lists none; cached rates appear in the chat models table (below). Models with no cached price there (Qwen3.5-9B, Qwen3.6-Plus, Qwen3.7-Plus, Qwen3.8-Flash, and the free Ternary-Bonsai-27B) show "-", and "Models without a cached input price bill every input token at the standard rate" (caching page) | https://docs.together.ai/docs/serverless/models.md, https://docs.together.ai/docs/inference/chat/prompt-caching.md |
| Minimum and granularity | Vary by model, not stated | same caching page |
| Lifetime | "Cache entries typically last about an hour. This is done on a best effort basis." On serverless the cache is shared across the fleet, so "under heavy load, entries may be evicted sooner" | same caching page |
| Routing | `prompt_cache_key`: a stable string on requests that share a prefix. Python SDK: `extra_body`; TypeScript and REST: top-level field. It "improves the odds of a cache hit but doesn't guarantee one". On dedicated endpoints it also serves as the sampling key for routing stickiness. No header is mentioned | same caching page |
| Price | Cached tokens bill at the model's cached input rate; other input at the standard rate; "There's no charge for writing to the cache." Dedicated inference has no cached discount (billed by GPU time) | same caching page |
| Rate limits | "Requests that hit the cache still count toward your rate limits." | same caching page |
| Usage field | Kimi K3: `usage.prompt_tokens_details.cached_tokens`. "Some models return `cached_tokens` at the top level of `usage` instead", so an auditor must check both places. The chat completions reference lists no cached field | same caching page, https://docs.together.ai/reference/chat-completions.md |
| Reasoning and cache | With preserved thinking, "all consecutive `reasoning_content` blocks must exactly match the original sequence generated by the model", otherwise "cache hit rates will drop" | https://docs.together.ai/docs/inference/chat/reasoning.md |
